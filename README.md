# афиша · MAX

Трек хакатона: **Досуг и развлечения**. Цифровое решение для поиска и организации досуга внутри мессенджера MAX: чат-бот и мини-приложение.

| Что | Где |
| --- | --- |
| Чат-бот | [t691_hakaton_max_bot](https://max.ru/t691_hakaton_max_bot) |
| Мини-приложение | кнопка «Открыть афишу» в боте; хост `https://events.versacegus.cc` |
| Локальный стек | `docker compose up --build` → http://localhost:8080 |

Основной пользовательский сценарий проверяется в клиенте MAX. Docker поднимает ту же мини-аппу и API локально для разбора стека. Платформу MAX внутри Docker воспроизвести нельзя — условия проверки описаны в разделе про внешние сервисы.

---

## Назначение решения

**афиша · MAX** — персональная афиша и навигатор событий внутри MAX. Гость ищет, куда пойти (афиша, волонтёрство, туризм, спорт), записывается, собирает компанию и держит поход как план. Организатор публикует события и площадки в отдельном кабинете того же мини-приложения.

### Пользователь и проблема

Задача сформулирована внутри трека (допустимо выбрать свою проблему в теме кейса). Формула:

> Горожанин 18–35 лет, который уже сидит в MAX, вечером хочет за 2–3 минуты понять, куда пойти сегодня (одному или с друзьями) и записаться, но афиша размазана по сайтам агрегаторов, страницам площадок и чатам, а бронь, друзья и напоминание живут в разных местах. Организатор при этом не может опубликовать событие там, где уже находится аудитория.

Актуальность: информация о досуге в городе разрознена (агрегаторы, сайты организаторов, соцсети). Пользователь совмещает интересы, время, место, бюджет и компанию вручную. Организатор ведёт расписание и запись вне мессенджера.

### Как есть → как будет

| | Как есть | Как будет |
| --- | --- | --- |
| Гость | Открывает несколько афиш, копирует ссылку в чат, отдельно бронирует | Один вход из MAX: бот подсказывает «что сегодня» / «куда пойти», мини-приложение показывает каталог, карту, запись и свои брони |
| Организатор | Публикует на своём сайте и в сторонних каналах | Кабинет в той же мини-аппе: события, места, люди, вход, промо, финансы как режим оплаты |
| Оплата | Билет на сайте организатора | Бесплатное событие записывается в приложении; платное ведёт на `paymentUrl` организатора (эквайринг платформы в MVP не подключён) |

Гипотеза: если собрать персональную афишу, запись и социальные сигналы внутри MAX, гость быстрее выбирает вечер, а организатор публикует событие там, где уже есть аудитория.

Ожидаемый эффект пилота: время от «куда пойти» до записи — минуты в одном клиенте; каталог Москвы и СПб наполняется сидом, кабинетом и живым импортом KudaGo; организатор видит записи и отзывы в одном кабинете.

### Масштаб: ядро и переменная часть

**Ядро** (переносится в другой город без переписывания продукта): идентификация через MAX `initData`, чат-бот, мини-приложение, каталог событий и мест, запись, кабинет организатора, жалобы и модерация.

**Переменная часть**: город и гео, набор внешних афиш, демо-наполнение ленты, социальный граф друзей, способ оплаты, льготные признаки (Пушкинская карта как флаг события).

## Основной пользовательский сценарий

1. Открыть бота [t691_hakaton_max_bot](https://max.ru/t691_hakaton_max_bot) в MAX, нажать «Начать» или отправить `/start`.
2. Получить приветствие с кнопкой открытия мини-приложения и пунктами меню (`/today`, `/whereto`, `/plans`, `/bookings`, `/help`, `/menu`).
3. Нажать «Что сегодня» (`/today`) или «Куда пойти» (`/whereto`: компания → настроение → бюджет) либо написать свободный запрос, например «джаз вечером».
4. Записаться на событие из чата или открыть мини-приложение кнопкой «Открыть афишу».
5. В мини-приложении пройти онбординг (город), открыть «Поиск» → «Популярное» или «Ближайшие события», открыть карточку, записаться. Бесплатное событие подтверждается в приложении; платное открывает ссылку оплаты организатора.
6. Увидеть запись в «Мои брони» (в приложении и командой `/bookings` в чате).

Локальный Docker повторяет мини-приложение и API в браузере. Чат-бот, вебхук и вход через MAX проверяются только в мессенджере на `https://events.versacegus.cc`.

## Состав и архитектура решения

Монорепозиторий:

| Часть | Путь | Роль |
| --- | --- | --- |
| Мини-приложение | `apps/app-miniapp` | React 19 / Vite / Ionic, MAX Bridge. Гость: лента, поиск, карта, создание, профиль. Организатор: статистика, события, продвижение, финансы, профиль |
| Backend API | `apps/svc-backend` | NestJS, TypeORM, чат-бот, импорт афиши, записи, кабинет |
| Контракты | `packages/api-contracts` | Zod-схемы запросов и ответов `/api` |
| Локальный стек | `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example` | Postgres, Redis, API, nginx с мини-приложением |

```
MAX (клиент)
  ├─ Bot API  ──webhook──►  backend :3100  ──►  postgres
  └─ Mini App ──HTTPS────►  nginx (статика + /api) ──►  backend
                                                      ──►  redis
backend по сети ──►  живые: KudaGo, Open-Meteo, Wikidata, OSM
                   ──►  по флагу/ключу: TimePad, OpenCode Zen
```

Аутентификация гостя: HMAC подпись `initData` мини-приложения MAX (токен бота). Кабинет организатора: login/password, сессия в Redis. Каталог: стартовый сид + импорт KudaGo + события организаторов и пользователей.

Собственный HTTP API: префикс `/api` на том же хосте, что и мини-приложение. Проверка живости: `GET /api/health/live`. Формы запросов и ответов — в `packages/api-contracts`. Тестовые учётки — в разделе про тестовые данные.

## Одна команда запуска (Docker)

Из корня репозитория, Docker Engine с Compose v2:

```bash
docker compose up --build
```

Поднимаются Postgres, Redis, API и мини-приложение. При старте backend выполняются миграции и стартовый каталог (`seed-cli`).

- Мини-приложение: http://localhost:8080
- API health: http://localhost:3100/api/health/live → `{"status":"ok"}`

Первая сборка занимает несколько минут. Повторный запуск без пересборки: `docker compose up`.

## Необходимые параметры окружения

Для **основного сценария в MAX** нужен установленный клиент MAX и доступ к боту `t691_hakaton_max_bot`. Платформу MAX внутри Docker воспроизвести нельзя.

Для **локального Docker** достаточно Docker. Файл `.env` не обязателен: `docker-compose.yml` подставляет значения по умолчанию (`MAX_BOT_TOKEN=local-dev-token`, `AUTH_ALLOW_BROWSER=true`, кабинет `max-events` / `demo-password-12`).

Чтобы подставить свой токен бота или пароль организатора, скопируйте `.env.example` в `.env` в корне — Compose подхватит `MAX_BOT_TOKEN`, `ORGANIZER_LOGIN`, `ORGANIZER_PASSWORD`. В `.env.example` нет рабочих секретов.

## Зависимости

- Docker Engine и Compose v2 — запуск всего локального стека одной командой.
- Сборка из исходников: корневой `Dockerfile` (цели `backend`, `backend-local`, `miniapp`), `docker-compose.yml`, `.dockerignore`, `.env.example` без рабочих секретов. Отдельные Dockerfile сервисов — в `deploy/`.
- Образы: `postgres:16-alpine`, `redis:7-alpine`, `nginx:1.27-alpine`, `oven/bun:1.3.14-debian`.
- Языки и пакеты зафиксированы в `bun.lock` (`packageManager`: `bun@1.3.14`). Backend: NestJS 11, TypeORM, pg, ioredis, zod. Мини-приложение: React 19, Vite, Ionic, MapLibre, Leaflet.
- Клиент MAX — для основного сценария (бот и мини-приложение внутри мессенджера).
- Исходящие вызовы к `platform-api2.max.ru` идут с сертификатами НУЦ Минцифры, они вшиты в образ backend (`deploy/certs/`).

## Описание работы с данными

- **Postgres** — пользователи (MAX id, имя, username, фото), профили и настройки приватности, места и события, брони, планы, лента, отзывы, жалобы, организации (пароль — scrypt).
- **Redis** — сессии кабинета организатора, кэш прогноза погоды.
- **Файлы** — загруженные изображения в `STORAGE_DIR` / volume `uploads`; статические обложки сида — в мини-приложении (`/covers/…`).
- **Вход** — сервер проверяет подпись `initData` ключом бота. Без валидного initData пользовательский API отвечает 401. Каталог и брони — от имени текущего пользователя; чужие брони и планы закрыты.
- **Геолокация** — браузер или webview; на сервере не хранится как обязательное поле. Координаты уходят в запросы «рядом» и маршрутов.
- **Секреты** — только в окружении, не в git. `.env` в `.gitignore`. `.env.example` содержит плейсхолдеры.

Факты афиши в MVP: дата и место события из своей БД, сида или ответа KudaGo. Расчёты (расстояние, «скоро», погода) помечаются интерфейсом как производные. Рекомендации «куда пойти» — эвристика по ответам пользователя, не официальный рейтинг. Синтетический CAST — заранее подготовленные данные для демонстрации ленты.

## Порядок работы с тестовыми данными

Локальный `docker compose up --build` сам прогоняет миграции и `seed-cli`:

- город Москва, места: Парк Горького, Третьяковская галерея, Столовая №57 ВДНХ, Лужники, ВДНХ;
- события четырёх категорий трека: «Джаз в Парке Горького» (афиша), «Субботник на ВДНХ» (волонтёрство), «Прогулка по Замоскворечью» (туризм), «Утренняя пробежка в Лужниках» (спорт);
- организация кабинета: логин `max-events`, пароль `demo-password-12`.

Гостевой вход в браузере: сборка Docker включает `VITE_BROWSER_AUTH=1`, мини-приложение запрашивает `POST /api/auth/browser-initdata` и получает подписанный initData учётки owner. Отдельная кнопка «Войти» на заставке появляется, если браузерный шим выключен.

Повторный seed идемпотентен (upsert по ключам каталога). Сброс данных:

```bash
docker compose down -v
docker compose up --build
```

На проде каталог наполнен сидом, импортом KudaGo и синтетическим CAST для городской ленты. Пароль боевого кабинета организатора в README не публикуется. Новый пользователь, вошедший через MAX, не получает чужие брони и друзей CAST.

## Пошаговый сценарий проверки

### A. Основной сценарий в MAX (обязательный)

1. Открыть MAX → бот `t691_hakaton_max_bot`.
2. Нажать «Начать» или отправить `/start`.
3. Нажать «Что сегодня» или отправить `/today`.
4. Нажать «Куда пойти» или `/whereto`, ответить на три вопроса.
5. Написать «джаз вечером».
6. Записаться кнопкой в чате или открыть мини-приложение.
7. В мини-приложении открыть «Поиск» → «Ближайшие события» или «Популярное», открыть карточку и подтвердить запись.
8. Проверить «Мои брони» в приложении и `/bookings` в чате.

### B. Локальный Docker

1. `docker compose up --build`
2. Дождаться `http://localhost:3100/api/health/live` → `{"status":"ok"}`.
3. Открыть http://localhost:8080 — гостевая оболочка (браузерный initData).
4. Онбординг: город Москва, если экран показан.
5. «Поиск» → карточка «Джаз в Парке Горького» (или другое событие сида) → «Записаться».
6. Кабинет организатора: выйти на заставку из настроек профиля → «Вход организатора» → `max-events` / `demo-password-12`. Вкладки: Статистика, События, Продвижение, Финансы, Профиль.

## Примеры ожидаемого поведения системы

- `/start` или «Начать» в боте: приветствие, кнопка открытия мини-приложения, пункты «Что сегодня» / «Куда пойти».
- `/today`: счётчики рядом и карточки с «Записаться».
- Успешная запись в чате: подтверждение; событие есть в `/bookings`.
- Нет мест: предложение листа ожидания.
- «Поиск» → «Ближайшие события»: только события с датой старта в будущем, по возрастанию даты.
- «Поиск» → «Популярное»: предстоящие события, сортировка по рейтингу.
- Бесплатное событие: запись создаётся в API. Платное: переход на `paymentUrl` организатора.
- http://localhost:3100/api/health/live → `{"status":"ok"}`.
- Запрос пользовательского API без initData → 401.
- Мини-приложение после входа: лента, карта, каталог, карточка сидового события.

## Известные ограничения

- Платформу MAX (бот, `initData`, вебхук) Docker не воспроизводит. Основной сценарий — в клиенте MAX на `events.versacegus.cc`.
- Список друзей MAX мини-приложению недоступен; на проде социальный граф пустой. В локальном Docker включён демо-режим «все пользователи — друзья».
- Встроенного эквайринга нет: платное событие ведёт на сайт организатора. `PAYMENT_PROVIDER=sandbox` — отладочный контур.
- Импорт TimePad без `TIMEPAD_TOKEN` не наполняет каталог (ответ API 403).
- Карта «Своя» читает PMTiles с прода (`/tiles`). Без сети до `events.versacegus.cc` эта подложка в локальном Docker пустая.
- Импорт KudaGo и погода зависят от внешних HTTP API; при их недоступности остаётся сид.
- `AUTH_ALLOW_BROWSER` и `FRIENDS_DEMO_ALL_USERS` на боевом MAX-хосте выключены.
- Признак «Пушкинская карта» — локальный флаг события.

## Остановка и повторный запуск

Остановить, сохранив базу и загрузки:

```bash
docker compose down
```

Запустить снова (без пересборки образов):

```bash
docker compose up
```

Пересобрать образы после изменения кода:

```bash
docker compose up --build
```

Полностью стереть тома (каталог, брони, загрузки) и поднять заново:

```bash
docker compose down -v
docker compose up --build
```

Логи: `docker compose logs -f backend miniapp`.
